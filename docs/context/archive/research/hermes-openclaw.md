# Ресёрч: Hermes (Nous) и OpenClaw — что взяли

Изучили архитектуру Hermes Agent (agent loop, gateway, sessions, компрессия, provider runtime) и
файловую модель OpenClaw/Soul (TypeScript, тот же стек — паттерны портируются прямее), чтобы
заимствовать решения в ядро продукта.

## Вывод

Интуиция про md-файлы (soul/user/memory) подтверждена обоими проектами; своя версия
(identity/knowledge/policies/learned) была уточнена таксономией и добавлены три инженерных приёма:
тиринг промпта+кеш, security-scan контекста, frozen-snapshot памяти. Общие принципы дизайна Hermes
(prompt stability, observable execution, interruptible, platform-agnostic core, tenant/profile
isolation) совпали с уже выбранным курсом.

## Hermes — что взяли

1. **Тиринг промпта** `stable → context → volatile` с явными границами кеша — стабильный префикс
   (идентичность+tool-guidance+политики) кешируется провайдером, volatile (memory snapshot, retrieved-
   чанки) инъектится отдельно → выигрыш в латентности и стоимости через prompt-caching.
2. **Security-scan + усечение контекст-файлов перед инъекцией** (prompt-injection, невидимый юникод,
   «ignore previous instructions», усечение до 20k 70/20 head/tail) — обязательная митигация OWASP
   LLM01/LLM07.
3. **Frozen-snapshot памяти на старте сессии** — правки пишутся на диск, но не мутируют уже собранный
   промпт до новой сессии/ребилда — чистая семантика + не ломает кеш.
4. **Provider runtime resolution** `(provider, model) → (api_mode, key, base_url)` — подтвердило
   архитектуру LlmPort/model_configs, ориентир для добавления RU-LLM провайдера.
5. **session_search (FTS)** — агент ищет в прошлых сессиях перед уточнением, не заставляя гостя
   повторяться → инструмент recall по истории гостя (Postgres FTS уже есть).
6. **Context compression** — лосси-суммаризация средних ходов при превышении бюджета токенов.
7. **DM pairing authorization** — паттерн привязки канала владельца (код → привязка), безопасно, без
   «магии».
8. **Cron как first-class agent-задачи** — подтвердил дизайн планировщика/Reporter/follow-up.
9. Итерационный бюджет (`max_turns`), строгие правила чередования ролей (никогда два assistant/user
   подряд) — учтено при склейке 4 авторов (guest/agent/owner/system) в LLM-сообщения.
10. **Interruptible run** — новое сообщение гостя, пока агент думает, отбрасывает текущий ответ,
    частичный в историю не попадает.
11. **Двойная компрессия**: агентная на 50% реальных токенов + gateway-гигиена на 85% грубой оценки
    (ловит накопление за ночь); алгоритм — дёшево вырезать старые tool-результаты → защитить границы
    → структурное саммари по шаблону → пересборка. Урок: модель-суммаризатор должна иметь контекст ≥
    основной модели, иначе саммари молча падает.
12. **Prompt caching `system_and_3`** (системный промпт + скользящее окно последних 3 сообщений) —
    до −75% input-токенов на мультитёрне; зависит от модели (для gemini-flash проверить отдельно).
13. **Gateway two-level message guard**: обычные сообщения — очередь+interrupt, `/approve /deny /stop`
    — inline в обход очереди, чтобы не словить гонку. Прямо закрывает гонки approval.
14. **FTS5 + trigram поиск** → взято как `tsvector` + `pg_trgm` для recall и кириллического поиска.
15. **Per-session учёт токенов и cost** (input/output/cache_read/cache_write) → питает дашборд
    cost/resolution и per-tenant cost circuit-breaker (OWASP LLM10).
16. **Cron-доставки не зеркалятся в историю диалога** — Reporter/кампании/follow-up не должны попадать
    в гостевой диалог, держать отдельно.
17. **Auxiliary routing по ролям** (vision/summarization/session-search/embeddings — каждый со своим
    провайдером и независимым fallback) — расширило дизайн ролей classify/generate/judge/embed.

## OpenClaw — файловая модель и что взяли

Таблица соответствия файлов агента (SOUL.md/IDENTITY.md/AGENTS.md/USER.md/TOOLS.md/HEARTBEAT.md/
MEMORY.md) уточнила таксономию памяти:
- разделить `identity.md` → `soul.md` (персона/тон/hard-limits, мелкий, кешируется) + метаданные;
- добавить `venue.md`/`owner.md` (аналог USER.md) — профиль заведения и владельца (средний чек,
  преференции, уровни одобрения) — закрывало пробел (сбор среднего чека, персонализация);
- `knowledge/` остаётся RAG (не грузим целиком, в отличие от OpenClaw);
- `policies/` — строгий 3-слойный + eval-гейт слой, не смешивать с персоной;
- `learned/` — approval-gated (НЕ авто-аппенд как у OpenClaw), но взята идея дневных рабочих заметок.

**Tool policy / sandbox (OWASP LLM06):** allowlist + deny побеждает при конфликте, per-agent policy,
3 уровня sandbox (off/non-main/all), `elevated`-инструменты всегда на хосте, но не обходят policy.
Взято: deny-wins, per-agent allowlist, sandbox для рисковых инструментов (browser/exec/HTTP).

**`security audit`/`doctor` CLI-самопроверка** → security-preflight в CI/деплое. **Config hot-watch с
валидацией** (невалидное отклоняется до применения) → zod-config. **Files = source of truth, индекс
производный** — закрепило модель памяти.

### ClawHavoc — урок ценой чужого инцидента

Открытый скилл-реестр ClawHub с авто-загрузкой всех установленных скиллов в каждую сессию привёл к
supply-chain катастрофе (янв 2026): вредоносные скиллы (стилеры, кейлоггеры), в т.ч. **запись малвари
прямо в MEMORY.md/SOUL.md для персистентности между сессиями** («sticky»-атаки — инъекция дремлет в
памяти и срабатывает через недели).

**Прямой урок для MCP-каталога:** каталог обязан быть курируемым + проверенным + в sandbox +
подписи/версии, НЕ open-install (OWASP LLM03 Supply Chain + A03). Валидирует решение: `learned` не
пишется автоматически моделью/скиллом, память-ревизии immutable, write-доступ к soul/policies
ограничен и integrity-checked.

## Что не взяли

- Авто-рост памяти без подтверждения (OpenClaw) — только approval владельца.
- «Жертвуем токенами, грузим всё» — вместо этого гибрид: персона/политики кешируются целиком, знания
  через RAG.
- 70+ инструментов / 20 платформ / 6 terminal-бэкендов (Hermes) — узкий whitelist, MVP.
- Их single-user «доверяй хосту» дефолты — для B2B-мультитенанта неприменимы: изоляция ВКЛ по
  умолчанию (RLS, per-tenant секреты, sandbox исполнения, без «elevated на хосте»).
- Стриминг ответа гостю (`onResponseChunk`-эквивалент) — инвариант: гостю не стримим, policy видит
  весь ответ целиком.

## Решение по n8n

n8n — в каталог MCP-интеграций (владелец подключает сам), не внутри системы и не как оркестратор
(реализация «Оси 3: любой MCP-сервер»), сроки MVP-3+. Governance железно: любой инструмент каталога
идёт через Policy Engine + approval для рисковых + аудит, default-deny, изоляция кредов per-tenant, вне
hot-path.

Взято из n8n: UX «подключи свои инструменты» как курируемый каталог; per-integration credential store
(шифрованные креды на тенанта); execution log на каждый запуск; templates → пресеты автоматизаций
(роль+знания+политики+каналы+инструменты); workflow-модель (триггер→условия→действия) без визуального
конструктора для владельца в MVP; AI Agent node как оркестратор — подтвердило агент-оркестратор + Tool
Registry.

Не взято: n8n как мозг/оркестратор, визуальный конструктор для владельца, n8n в hot-path, вшивание
движка внутрь системы.
