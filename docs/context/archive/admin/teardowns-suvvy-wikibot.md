# Теардауны Suvvy и Wikibot

Личные прогоны двух конкурентов (11.06.2026). Их слабость — промпт/JSON-как-интерфейс (владелец бизнеса не будет редактировать секции промпта типа #ЦЕЛИ); у Suvvy агент молчал на «привет» в тестовом чате. Approval-слоя нет ни у кого на уровне модели данных — наша дифференциация структурная, не маркетинговая.

## Suvvy: что увидел

Онбординг генерирует большой структурированный промпт с #секциями, который дальше редактируется как текст вручную; есть «Аудит инструкции» и история версий. Тестовый чат: на «привет» агент не ответил — первое впечатление сломано (разгадка: `merge_message_time_seconds: 10` — намеренная задержка склейки сообщений, но пользователю это не объясняется).

### Разбор конфига агента (JSON)

Архитектура — весь агент это одна большая текстовая инструкция + плоский конфиг, без policy-слоя, ролей и прав. Сгенерированная инструкция содержала мусор: незаполненные шаблонные комментарии в проде и артефакт генератора «Ты — менеджер по продажам компании нет».

Что есть по конфигу: перехват сотрудником (`interception_by_employee` + `sleep_time_minutes: 60` — грубый аналог handoff, только «молчать», без approvals); уведомление «какой документ сработал» (для настройщика, не отчёт владельцу); поля безопасности существуют, но выключены (`personal_data_masking: null`, `memory.is_enabled: false`); монетизация интеграторов зашита в схему (`price_percent`); anti-spam, vision, разбиение ответов, голос (ElevenLabs), reminders, structured output, vector search top-3 порог 0.5, лимит 10 tool calls, LLM — GPT-4o.

Интеграции Suvvy = их вертикали: YCLIENTS, Altegio (салоны красоты), MedFlex (клиники), amoCRM/Kommo/Bitrix24, ЮKassa/Продамус. Общепита у них нет — ни iiko, ни r_keeper, ни бронь столиков.

В схеме данных нет: approval-flow (только «позвать менеджера»), классификации риска действий, прав/ролей агента, отчётов владельцу, аудита решений. Чтобы добавить этот слой, конкуренту нужно перепроектировать ядро.

### Уроки для продукта

Склейку сообщений делать, но показывать индикатор «печатает» — не молчать. Уведомление «какой источник сработал» развить до полноценного отчёта владельцу. `price_percent` для интеграторов заложить в схему биллинга с первого дня. Генерация онбординга не должна оставлять шаблонный мусор. Платёжные интеграции (ЮKassa) сознательно вне MVP — деньги без approval-слоя пугают владельцев.

## Wikibot: что увидел

JSON и REST API показываются пользователю напрямую — интерфейс для технарей. «Навыки» — пара строк промпта (Полиглот, Фильтрация, Выбор исполнителя, Редактор), «сценарии» — тоже просто промпты без ветвлений и гарантий. Интеграция с CRM — только amoCRM + произвольные HTTP-запросы. «Первая линия» (быстрые ответы до LLM) реализована как ручная форма — идея здравая, исполнение слабое. Есть глоссарий терминов (хорошая идея, взять в RAG-слой). Алертинг и приличные дашборды есть у обоих конкурентов.

## Общий вывод (УТП)

Простота для пользователя без тех-бэкграунда. Оба конкурента строят интерфейс для настройщика-технаря (промпты, JSON, REST, формы). Никто не строит для владельца бизнеса. «Первая линия», «навыки» и «сценарии» в нашем продукте должны рождаться из диалога с агентом и работы системы, а не из форм — архитектурно это отдельный дешёвый модуль пайплайна до LLM (exact/semantic match по подтверждённым ответам), а не промпт-сниппеты.

## Историческая заметка про выбор вертикали

Раздел выбора между общепитом и консалтингом как первой вертикали в оригинале помечен как исторический — актуальное решение (общепит-дверь → класс SMB с бронями, затем разворот на персональные автоматизации) зафиксировано в других заметках/решениях проекта.
