# Вопросы и решения — производство (архив, отвечено 14.06.2026)

Большой раунд производственных решений по вертикали общепита (администратор ресторана/кафе) — до разворота на персональные автоматизации (см. «Отменённые решения»). Материал сохранён как исторический контекст и как рабочий шаблон для будущей вертикали общепита.

## Критичные решения (безопасность/качество/сроки)
- Аллергены без импорта меню: сузили обещание — при отсутствии точного совпадения всегда approval, «точное совпадение» осталось на MVP-2.
- Eval-датасет (FN≤2%) — стартовать на синтетике + кейсах из теардаунов, реальные кейсы доливать из кастдева, не ждать 50 реальных кейсов.
- Латентность с PII-редакцией — детерминированный redaction (regex + лёгкий NER, ≤300мс); при низкой уверенности сразу approval, без третьего LLM-вызова, чтобы не рвать бюджет 10с.
- OpenRouter (отказ и тихий дрейф модели) — пиннинг версий где возможно + ночной ретро-eval + РФ-fallback (GigaChat) как «спасательный круг».
- Корректность обратной подстановки PII — хранить маппинг отдельно, валидировать неизменность плейсхолдеров в ответе; при расхождении — не отправлять, approval.
- Перегрузка фаундера (разработка+QA одновременно) — вынести eval-разметку и часть тестов на продажника/ИИ-ассистента, фаундер оставляет за собой ядро и приёмку.

## Важные решения
- Тон агента — «tone golden set» + LLM-judge ≥4.2 в CI; владелец персоны — фаундер+контент.
- Голосовой канал — честно вне MVP-1, но «перехват пропущенного звонка → текст агенту» как ранний эксперимент.
- Холодный старт базы знаний — батчить K2-пуши в дайджест с первого дня + максимально предзаполнять базу на онбординге.
- Single-VPS как SPOF на пилоте — принять риск на 1–3 клиента + горячий рестор-рунбук; HA только после 3+ платящих.
- SLA-таймеры в Redis — дублировать критичные таймеры в Postgres-outbox с reconciler.
- Overage-биллинг (10₽/диалог) — копить и прощать до мягкого порога, предупреждать заранее, не выставлять сюрпризом; уведомлять при приближении к 50% лимита.
- Ручной ревью авто-ответов в первую неделю пилота — фаундер/владелец ежедневно смотрит выборку «safe auto-sent».

## Средние решения
- Фото от гостя (чек/блюдо/меню) — вежливая эскалация «передам владельцу» в MVP-1, vision — P1.
- Многоязычность — не давать «из коробки» без проверки; не-RU языки добавляются только после расширения eval-датасета.
- Анти-спам/абьюз — базовые лимиты + «свернуть за 1 ответ» для не-гостя достаточно для MVP-1, но нужно прописать систему анти-спама и её масштабирование отдельно.
- Лимиты Telegram (30 msg/s) — очередь отправки с backoff в MessengerPort, приоритет approval-ответам.
- Рост контекста промпта — жёсткий токен-бюджет (identity + pinned ≤800 + top-4 + обрезка истории).
- Тест восстановления из бэкапа — один restore-drill в QA-чеклист пилота.
- Экспорт/удаление данных тенанта — отложено (не в MVP-1).
- Смена embedding/LLM-модели — регламент: смена модели → CI-eval + фоновая переиндексация.

## Лёгкие решения
Приняты по рекомендациям: DOMPurify против stored-XSS из базы знаний; дедуп TG-вебхуков с фолбэком в Postgres при сбое Redis; часовые пояса per-location в UTC с тестом на DST; демо-тенант на Fake-адаптерах (в виде отдельного аккаунта); WCAG AA перед хендоффом фронта; hold-режим для сезонной паузы (данные хранятся, агент офлайн); 5-строчные мини-спеки + Fake-адаптеры для онбординга команды.

## Глубокий тех-аудит (доп. 13.06)
- База знаний в OpenRouter пересекает границу РФ — для общепита принято как допустимо (меню/FAQ не гостайна) с дисклеймером в оферте/DPA; для чувствительных вертикалей — RU-LLM на весь контур.
- Устойчивость классификатора риска к prompt-injection — вывод LLM-классификатора считается недоверенным, детерминированные level-0 guard'ы и locked-политики имеют приоритет; инъекционные кейсы добавлены в eval.
- Генерация `seq` сообщения под конкуренцией — атомарный счётчик через `UPDATE...RETURNING` в одной транзакции.
- Один Redis на durable+эфемерное — разнести на разные инстансы/логические БД с разными политиками вытеснения.
- Per-tenant concurrency в BullMQ — обеспечить справедливость per-tenant (groups/rate-limit), не глобальная очередь.
- Своя FSM-либа для ядра (approval/бронь/онбординг) — решили вернуться к XState вместо кастомного автомата.
- Модель столов/вместимости — не авто-подтверждать посадку в MVP-1 (default-deny), столы/вместимость — MVP-2 с iiko.
- Партиционирование `events` — принят вариант B (партиции создаются впритык, риск принят, а не заранее на 2-3 мес).
- Retention сообщений 90 дней против юр-споров — для risk-flagged диалогов (аллерген/жалоба/компенсация) держать долгую архивную копию в S3, с заделом на масштабирование.
- TG webhook-secret — только в header (constant-time), не в path, с ротацией.
- Фильтр embedding_model при ретриве — инкапсулировать в единственной точке `Memory.retrieve()`.
- PK — зафиксирован UUIDv7 (не ULID).
- Общий чек-лист DoD/QA принят без отдельных решений (токены дизайна между сборками, виртуализация списков 50+, аудит SECURITY DEFINER, citext+pgvector на Timeweb, CSRF/cookie на SSE, стоимость test-chat в trial-счётчиках, дуннинг подписки, cron-очистка технических таблиц и др.).

## Точные определения (канон, все подтверждены «ок»)
- North Star: диалог, закрытый агентом без единого касания человека (ни approval, ни сообщения владельца) за неделю; approval без правки не входит в NS, трекается отдельно как «лёгкое касание».
- Resolution rate: (auto-resolved + assisted) / все закрытые диалоги; цель MVP-1 ≥60%.
- Инвариант «не молчит ≤10с» относится к первой видимой реакции (typing/holding), не к финальному ответу; auto p95 ≤10с, approval-ответ = время владельца + undo.
- Risk-матрица MVP-1 (safe/approval/blocked) зафиксирована таблицей: FAQ, бронь-заявка <8 чел, точный аллерген, эмпатия при жалобе, перенос/отмена без денег — safe; подтверждение посадки, неточный аллерген, группы ≥8/банкет/депозит, компенсация, скидки — approval; замена людей/мед/юр-консультации/tool вне реестра — blocked.
- SLA-таблица (минуты): аллерген-approval 10, жалоба 15, банкет/деньги 60 (днём), «вопрос без ответа» 15, «позвать человека» 10.
- Undo (задержка отправки 30с после ✅) принят как исходное решение вместо альтернативы «отправить и удалить».
- Счёт денег в отчёте — герой-число это подтверждённые заявки × средний чек, с явной пометкой «заявки, не гарантированный визит»; `requested` отдельно как «в ожидании».
- Тихие часы — две разные сущности: часы заведения (текст гостю ночью, старт SLA с открытия) и тихие часы владельца (не слать некритичное, критичное — всегда).
- Реестр инструментов агента MVP-1 (default deny): разрешено answer_from_kb, create_booking_request, reschedule_booking (без денег), ask_owner, handoff_to_human, log_unanswered; через approval — confirm_seating, give_discount, send_payment, send_campaign.
- Критерий успеха пилота: на ≥3 из 3-5 пилотов за ≥4 недели — resolution ≥60%, p95≤10с, 0 инцидентов с аллергенами, ≥30 auto-resolved диалогов/нед, владелец открыл ≥50% недельных отчётов → go на MVP-2.

## Дизайн/UX решения
- Handoff-идентичность: гость всегда видит явный переход («На связи Марина (владелец)»), агент не маскируется под человека.
- Тексты гостю: системные — шаблоны тенанта, содержательные — LLM в тоне персоны, рисковые (дисклеймер аллергена) — фиксированный обязательный текст.
- Уровень доверия (геймификация) в MVP-1 — информационный бейдж без авто-применения автономии; реальная разблокировка — MVP-2.
- Защита свайпа от случайной ✅-отметки: порог 60% + haptic, только для safe-одобрений; аллерген/деньги — только двойной тап; любой свайп → UndoToast 30с.
- Предложение авто-правила — инлайн-вставка после 3 ✅, необязательное, дефолт «позже».
- Таймер ожидания гостя — нейтральный счётчик, цвет risk только после нарушения SLA, без паники/красного мерцания.
- Политика уведомлений: аллерген/жалоба/просрочка SLA/падение бота — немедленный пуш всегда; банкет/деньги — немедленно днём, в тихие часы владельца — до окна; обычные approval и ночные события — дайджест ≤1/день; геймификация — никогда не пуш.
- Онбординг считается пройденным при: часы работы, ≥1 контакт, базовые FAQ, средний чек, канал владельца, тест-диалог, минимальный набор аллергенов.
- Геймификация MVP-1: входит прогресс онбординга, цепочка активации 1-й недели, уровень доверия как информационный бейдж, еженедельный ритуал (понедельник); НЕ входят стрики-наказания/очки/лидерборды/конфетти/ежедневные нуджи (это B2C-набор, вне MVP).
- Тон по контексту: обычное — тёплый живой с ≤1 эмодзи; аллергены/жалобы/деньги — серьёзный, 0 эмодзи, обязательный дисклеймер; никогда не использовать канцелярит/КАПС/панику.
- Realtime-разрывы UI: SSE/WS drop → плашка «обновлено N мин назад» + pull-to-refresh, досинхрон по last-event-id/seq при reconnect.
- Гейт валидации прототипа: 5 юзер-тестов, провал = ≥2/5 бросили онбординг, ≥2 одобрили approval не читая сумму, никто не поверил числу экономии.

## Безопасность (минимальная планка)
OWASP Top 10:2025 (веб) + OWASP Top 10 for LLM Applications 2025 как обязательная планка, входит в DoD каждого эпика. На момент фиксации закрыты: RLS, крипто, инъекции SQL/XSS, insecure design, аутентификация, целостность/CI, fail-closed, poisoning через approval, output handling, excessive agency (whitelist+approval), vector RLS, misinformation-защита. В backlog: SCA/Dependabot/пиннинг образов, security-события/алерты на аномалии авторизации, hardening-чеклист, инъекционный тест-сьют, пиннинг версий моделей, per-tenant cost circuit-breaker, redaction PII перед LLM.

## CI/CD принципы
- «Мозг» агента (промпты/политики/знания) — данные в БД с активацией через eval-гейт и горячий перезалив, не деплой кода.
- Near-zero-downtime rolling: 2 реплики за nginx, деплой по одной с healthcheck, graceful drain.
- Входящие не теряются во время деплоя: вебхук → Postgres-inbox → 200 сразу.
- Миграции expand/contract, двухфазно, без destructive-изменений в одном деплое.
- Авто-rollback при провале healthcheck/smoke; prod — по тегу + manual approve.
- In-flight agent-run не теряется (идемпотентная BullMQ-джоба с jobId=runId).
- Feature flags: деплой ≠ релиз.
- Гейты до прода: build+test+RLS-тест+eval-гейт+bundle-size на staging → smoke → prod.
- SLO деплоя: гость получает первую реакцию ≤10с или сообщение остаётся в очереди — ноль потерянных входящих (RPO 0).

## Продуктовые идеи (14.06)
- Веб-поиск: для гостевого B2B-агента MVP-1 — без открытого веб-поиска (конфликт с grounded-ядром и OWASP-рисками); открытый веб-поиск — только как B2C-фича в будущем личном ассистенте.
- Голосовой ввод (STT на голосовые сообщения в TG/веб) — брать рано (MVP-1/2), это массовое поведение в СНГ; голосовые звонки в реальном времени — отдельный продукт, MVP-3.
- Онбординг через ingest источников (NotebookLM: сайт + меню → авто-карточки знаний и таблица аллергенов) — поднять в приоритет.
- Missed-call → text-back в Telegram — рассмотреть для MVP-2 вместо MVP-3, сильный ROI-хук.
- iiko как канал дистрибуции (не только интеграция) — после первых кейсов рассмотреть партнёрство/листинг в iiko-маркетплейсе как канал GTM.
- Альтернативный слот при «занято» — фича MVP-1/2 в сценарий брони.
- Карта знаний (Mind Map) + «агент знает N о вас» — MVP-2.
- Двойная компрессия диалога для длинных ночных цепочек — MVP-2, в MVP-1 простой токен-бюджет.
- Supervisory-агент («полицейский») для риск-критичных ответов — подтверждён как P1.
- Разделение identity.md на soul.md (персона/тон/hard-limits) + метаданные — принято.
- Усилить недельный отчёт ROI-фреймингом «возвращённая выручка + сэкономленный труд».

## Регламент retention/удаления (пороги, приняты по умолчанию)
Messages hot 90 дней → S3 → delete; risk-flagged (аллерген/жалоба/компенсация) — хранить 1 год; партиции events старше 12 мес — drop; анонимизация PII гостя при неактивности 12 мес; удаление неактивного тенанта — 12 мес без входа (уведомление за 30 дн); self-delete grace 30 дней → hard-purge; crypto-shred ключа PII при удалении. Окна планировщика: недельный отчёт — понедельник 8:00–11:00 по tz локации + джиттер по тенанту; тяжёлые job'ы (архивация/cleanup/retro-eval) — глубокая ночь.
