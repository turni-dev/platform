# Каналы и нотификации

## Telegram-боты: создание и подключение

Telegram Bot API не позволяет создать бота HTTP-запросом «с нуля». Два официальных пути:

1. **Обычный бот через @BotFather** — пользователь создаёт бота вручную (`/newbot`), получает токен, вставляет токен в наш сервис. Мы проверяем токен через `getMe`, сохраняем, подключаем webhook/polling. Нельзя получить токен чужого обычного бота через Bot API.
2. **Managed Bots flow** — наш бот-менеджер (с включённым Bot Management Mode) даёт пользователю ссылку вида
   `https://t.me/newbot/{manager_bot_username}/{suggested_bot_username}?name={suggested_bot_name}`.
   Пользователь подтверждает создание в Telegram → менеджер получает update → backend вызывает `getManagedBotToken` → сохраняет токен → далее управляет ботом через обычный Bot API. Токен managed-бота можно перевыпустить через `replaceManagedBotToken`.

**Для SaaS поддерживать оба сценария**: подключение существующего бота по токену + создание нового через Managed Bots.

Ключевые методы Bot API: `getManagedBotToken`, `replaceManagedBotToken`, `setWebhook`, `getUpdates`, `sendMessage`. Массово создавать ботов одним серверным запросом без участия пользователя нельзя.

## Бизнес-интеграции

| Интеграция | Когда | Заметка |
|---|---|---|
| Своя книга броней (Postgres) | MVP | Каноничная схема: заявка → approval → FSM-статусы; без внешних систем |
| Google Sheets | не в MVP | Легаси-идея отклонена; кастомизация через `settings(jsonb)` + md-знания, внешние системы — за `BookingSystemPort` |
| iiko | MVP-2 → MVP-3 | Важнейшая интеграция вертикали (см. ниже) |
| Google Calendar | P1 | Консалтинг-трек; OAuth-верификация 2–4 нед |
| amoCRM | P1 | Консалтинг; Битрикс24 — P2 |
| Restoplace | P2 | Альтернатива iiko-резервам для малых |
| YCLIENTS | отложено | Зона другого продукта (салоны) |

**План iiko**: MVP-2 — read-only меню + стоп-лист + вебхук обновлений → MVP-3 — reserves read (агент видит занятость) → MVP-3+ — reserves write (бронь/банкет через approval, предоплата позже). Подключение: API-логин iikoWeb, токен на 1 час, лицензия Cloud API через дилера. Killer-фича: вебхук стоп-листа снимает риск «бот наврёт про наличие». Риски: зависимость от дилера, расхождение ID столов, нужен сендбокс.

**Правило добавления интеграции**: брать только если (а) просят ≥3 платящих или 1 якорный ≥20% MRR, (б) публичный API без партнёрской сертификации, (в) ≤2 недель одного разработчика. Иначе — ручной обход через approval-карточку.

## Корпоративная почта (транзакционные письма)

- Провайдер: **REG.RU Mail hosting / SMTP** (не Unisender, не свой SMTP на VPS). Домен `turni.ru`, DNS/MX уже в REG.RU.
- Тариф Mail-1: 10 ГБ SSD, 1 почтовый домен, до 1000 ящиков, до 3000 писем/сутки.
- Отправитель: `noreply@turni.ru`, Reply-To: `support@turni.ru`.
- SMTP: `mail.hosting.reg.ru:465`, implicit TLS (`SMTP_SECURE=true`). Порт 25 для доставки не использовать.
- Приложение отправляет через `EmailPort` → `SmtpAdapter`; секреты — только в `sops/age` (не в коде/чате).
- Причина не поднимать свой SMTP: репутация IP, PTR/rDNS, TLS, bounce handling, blocklist monitoring, прогрев — избыточно для критичного пути auth-кодов в MVP.
- В логах — редактировать тело письма; логировать только provider message id, hash получателя, ключ шаблона, статус доставки. Таймауты/ретраи — в адаптере/воркере очереди, не в domain-коде.
- DNS настроен: SPF, DKIM (`dkim._domainkey`), DMARC (`p=none`).

## Нотификации — регламент (NotificationService)

Единая подсистема поверх `NotifyPort`. Принцип: **тишина по умолчанию** · granular-преференции (не один тумблер) · critical — мгновенно и в обход тихих часов · ноль потерь и дублей.

### Каналы (для владельца; гостю — ответ в самом чате, не «нотификация»)
- **In-app / SSE (кабинет)** — всегда; источник правды, resume по last-event-id.
- **Telegram** — пуш с deep-link, inline-решения для безопасных действий.
- **Email** — код входа (критично), счета, дайджесты, fallback.
- **Web Push (PWA)** — опционально, MVP-2.
- **SMS** — только критичный fallback (когда TG и email не дошли), P2.
- Fallback-лестница: critical → in-app + (TG или email); нет доставки за N мин → второй канал → SMS для самого критичного.

### Таксономия событий (приоритет → канал → тихие часы)
| Событие | Приоритет | Канал/режим | Тихие часы |
|---|---|---|---|
| Код входа (auth) | transactional-critical | email <1 мин | игнор |
| Смена email / новый вход | transactional-critical | email немедленно | игнор |
| Аллерген-approval / жалоба / просрочка SLA / инцидент | critical | in-app + TG/email немедленно | bypass |
| Банкет/деньги-approval | important | немедленно днём | отложить до окна |
| Обычный approval | important | in-app + батч | дайджест |
| «Вопрос без ответа» | info | дайджест ≤1/день | дайджест |
| Недельный отчёт | info | пн, окно по tz | по окну |
| Счёт/квитанция | transactional | email | — |
| Приближение к лимиту overage (50%, 80%) | important | заранее, in-app + дайджест | — |

### Маршрутизация и анти-fatigue
- `users.notify_prefs` (jsonb): per-категория × per-канал + тихие часы + каденс дайджеста; настраивается в S1 → «Уведомления».
- Нельзя отключить critical (можно только выбрать канал); transactional (код входа) — без opt-out.
- Дайджест time-based (утро/вечер) или event-based (накопилось ~5); группировка по ключу; дедуп через idempotency key = `event_id + user + channel`. Цель: ≤5 карточек/день к неделе 4.
- Тихие часы — две сущности: часы заведения (текст гостю ночью + старт SLA с открытия) и тихие часы владельца (не слать некритичное; critical всё равно идёт).

### Надёжность и безопасность
- Decoupled очередь (BullMQ `notifications`) + pub/sub + outbox (не терять при сбое Redis).
- Ретраи с exp backoff на retryable ошибках, circuit breaker per-канал, dead-letter + алерт.
- Idempotency key фиксируется в сторе до вызова провайдера.
- Трекинг доставки: sent/delivered/failed/opened; метрики delivery rate, latency, «approval не просмотрен >2ч» → алерт.
- PII-минимизация в теле push/SMS (без чувствительных данных на локскрине); согласие/opt-out для исходящих гостю (кампании), не для transactional/auth. Аудит доставки критичных. 152-ФЗ: данные в РФ (REG.RU Mail / RU-SMS).

### Реализация и roadmap
`NotificationService` поверх `NotifyPort` (адаптеры TG/email/push/SMS): событие → resolve преференций → выбор канала(ов) → батч/немедленно → отправка с ретраями/fallback → трекинг статуса. Шаблоны локализованы (ru), брендированы.

- MVP-1: in-app/SSE + Telegram + Email + дайджест + тихие часы + преференции в S1.
- MVP-2: Web Push, расширенные преференции.
- P2: SMS-fallback.
