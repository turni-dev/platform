# Tenant secret encryption — slice plan

**Card:** `Доска MVP-1` → С2a [M1 Core] Шифрование tenant-секретов (CURRENT).
**Notes:** `Безопасность и доверие` (A04: AES-GCM per-purpose ключи `v1:`),
`Схема БД — детально` (`credentials_enc text`, формат `v1:iv:ct:tag`),
`Тех-решения (консилиум)` (per-purpose ключи в sops, phone_enc тем же способом).

**Goal:** one proven place through which a tenant-scoped secret reaches the
database encrypted, so the Telegram and Google cards consume it instead of each
inventing its own crypto.

## What already exists

- `channel_connections.credentials_enc text` since `0003_channels.sql`. No
  migration is needed, and none is wanted on this card.
- `KEY_CREDENTIALS_V1` — 32 random bytes, base64 — is already generated by
  `tools/bootstrap/secret-bootstrap.mjs` into `ops/sops/secrets.enc.json`,
  alongside `KEY_PHONE_V1` and `PEPPER_V1`. The `_V1` suffix is the key version.
- There is no `createCipheriv` anywhere in the repository today.

## Decisions taken from the notes (not invented here)

- **Format `v1:iv:ct:tag`** is prescribed by `Схема БД — детально`. The version
  is the key version, not a format version, so rotation is a key change alone.
- **AES-256-GCM, per-purpose keys** is prescribed by `Безопасность и доверие`
  (A04). Channel credentials and `guests.phone_enc` are different purposes and
  therefore different keys — the primitive is built per purpose from the start.

## Judgement calls (flagged for founder review at close)

- **AAD binds the ciphertext to `{purpose}:{tenantId}`.** Under FORCE RLS a
  ciphertext cannot normally travel between tenants, but a backup restore, a
  mis-scoped repair script or a future admin path could paste one row's value
  into another tenant's row. With AAD that paste fails to decrypt instead of
  silently succeeding. The cost is that a tenant merge would require
  re-encryption; there is no tenant merge in MVP-1.
- **Decryption never explains itself.** A wrong key, a truncated segment and a
  flipped tag all raise the same error with no plaintext, no key material and no
  segment detail, so the error is safe to log and useless to an attacker probing
  which part he got wrong.
- **Encrypt with the newest known key, decrypt with any known key.** Rotation is
  then: add `KEY_CREDENTIALS_V2` to sops, deploy, re-encrypt at leisure, drop V1.
  No code change, no downtime, and old rows keep working meanwhile.

## Global constraints

- No migrations, no `packages/contracts` changes: the primitive is internal, it
  crosses no external boundary, so it lives in `apps/backend/src/platform/crypto`
  next to `platform/database` and `platform/cache`.
- Never log or throw plaintext, ciphertext or key material.
- The decrypted secret never reaches the UI, an analytics event, or a prompt.
- New tests live in sibling `__tests__/` directories.

## Slices

### Slice 1 — The key ring

- Parse `KEY_CREDENTIALS_V*` out of env with Zod: base64, exactly 32 bytes,
  version a positive integer. Build a ring that answers "the newest key" for
  encryption and "the key for version N" for decryption.
- Reject a ring with no keys at startup rather than at first use, so a
  misconfigured deployment fails on boot like the rest of `env.ts` does.
- Acceptance: a key of the wrong length is refused; a non-base64 key is refused;
  V2 present makes V2 the encryption key while V1 stays readable; an empty ring
  is a startup failure; the error text never contains the key.

### Slice 2 — The AES-256-GCM cipher

- `encrypt(plaintext, { purpose, tenantId })` → `v1:iv:ct:tag`, a fresh 12-byte
  IV per call, AAD over purpose and tenant.
- `decrypt(ciphertext, { purpose, tenantId })` → plaintext, or one generic
  error for every failure mode.
- Acceptance: a round trip returns the original including non-latin text; two
  encryptions of the same input differ (fresh IV); a flipped bit in any of the
  four segments fails; another tenant's context fails; an unknown key version
  fails; the same value encrypted under V1 still decrypts after V2 is added.

### Slice 3 — Wiring and the real round trip

- Read the ring in `platform/env.ts`, build the cipher in the composition root,
  document the key in the deployment notes and write ADR 0007.
- Store an encrypted value into a real `channel_connections.credentials_enc`
  row under `withTenant` against live Postgres and read it back — the previous
  two cards both found defects that fakes hid, so the column is proven, not
  assumed.
- Acceptance: the stored column matches `^v1:` and contains none of the
  plaintext; the value decrypts inside the owning tenant's context; a second
  tenant reading the same literal string fails to decrypt.
