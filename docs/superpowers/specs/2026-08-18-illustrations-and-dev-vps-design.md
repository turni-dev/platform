# Иллюстрации сайта и Ubuntu dev-стенд

## Цель

Подготовить два операционных документа: единый пакет промптов для правдивых
иллюстраций корп-сайта и воспроизводимый запуск всего монорепозитория на одном
Ubuntu VPS для dev-стенда с HTTPS и непрерывной поставкой из GitHub.

## Границы

- Иллюстрации не попадают в репозиторий: их генерируют по документу и загружают
  в Strapi CMS. Каждому файлу нужны alt-текст, WebP или AVIF и разумный вес.
- В первом пакете ровно три слота: hero главной, схема обвязки агента и схема
  развёртывания в контуре клиента. Мок-скриншот описывается как отдельный
  переиспользуемый компонент, а не как доказательство несуществующей функции.
- Dev-стенд состоит из двух отдельных Docker Compose-проектов: существующий
  `compose.site.yml` для сайта/CMS и существующий `compose.yml` для продукта.
  Базы и docker-сети не объединяются.
- Caddy — единственная публичная точка входа: `turni.ru` ведёт на core-site,
  `cms.turni.ru` закрыт basic auth и IP allowlist, продуктовые `app`/`api`
  домены направляются только после появления работающих сервисов.
- Секреты не попадают в GitHub, `.env` или историю shell. SOPS/age остаётся
  источником секретов; на VPS запускаются только временно расшифрованные файлы
  с правами `0600`.
- GitHub Actions собирает и публикует версии образов в GHCR, а отдельный
  ограниченный deploy-пользователь выполняет ровно проверенный deploy-скрипт.
  В текущем репозитории нет production ingress и pipeline site-образов;
  runbook должен явно разделить уже имеющееся и требующее следующей карты.

## Критерии готовности документов

1. Каждый промпт использует одну общую визуальную систему, конкретный сюжет и
   отрицательные ограничения: никаких лиц, фальшивого интерфейса, чужих
   логотипов и обещаний несуществующих функций.
2. Runbook можно пройти на чистом Ubuntu VPS без догадок: подготовка сервера,
   firewall, Docker, DNS, Caddy, SOPS, два Compose-стека, проверки и rollback.
3. Runbook отмечает действия владельца и не предлагает хранить приватные ключи
   age либо production-секреты в GitHub Actions.

## Риски и решения

- Один VPS не равен production-изоляции: документ называет его dev-стендом и
  не переносит туда production-данные.
- CMS никогда не публикуется открыто: доступ ограничен сетево и паролем.
- Если CI/CD ещё не реализован, документ описывает предварительные условия и
  целевую схему, а не команды, которые в текущем состоянии ложно обещают
  автоматический деплой.
